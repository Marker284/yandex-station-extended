# Как внести вклад

Спасибо, что помогаете вики! Здесь — как предложить правку, как оформить текст и что писать
в pull request. Про то, **куда** класть материал и какие данные снять с новой модели, —
страница [«Как дополнять вики»](https://hackalice.me/contributing/) на сайте.

## Способы

| Что у вас есть | Что сделать |
|---|---|
| Опечатка, правка, новая страница | ✏️ карандаш на странице сайта → редактор вики → **Отправить правку** (PR создаётся сам) |
| Новый раздел, инструкция, скрипт | fork → ветка → PR (ниже) |
| Данные о модели, но нет времени оформлять | [issue «Данные о модели»](https://github.com/Marker284/yandex-station-extended/issues/new/choose) — оформим сами |
| Инструкция не сработала | [issue «Ошибка в инструкции»](https://github.com/Marker284/yandex-station-extended/issues/new/choose) с моделью, прошивкой и выводом команд |

## Pull request шаг за шагом

1. Сделайте fork и ветку с понятным именем: `station-3-uart`, `fix-ssh-autostart`.
2. Внесите правки в `docs/` (и `mkdocs.yml`, если добавили страницу) или в `contrib/`.
3. Соберите сайт локально и убедитесь, что нет предупреждений:

    ```sh
    python3 -m venv venv
    ./venv/bin/pip install -r requirements.txt
    ./venv/bin/mkdocs build     # без WARNING и без INFO про битые ссылки и якоря
    ./venv/bin/mkdocs serve     # предпросмотр на http://127.0.0.1:8000
    ```

4. Откройте PR в `main` и заполните шаблон: что добавлено, на какой модели и прошивке
   проверено, как проверяли.

После проверки PR сливается через **squash merge**. Если нужны мелкие правки оформления,
мы сделаем их сами следующим коммитом — переделывать PR не придётся. Автор попадает на
страницу [«Участники»](https://hackalice.me/contributors/).

## Оформление текста

- **Только проверенное.** Пишите, на какой модели и прошивке проверено. Догадки помечайте
  явно («не проверялось», «похоже»).
- **Сначала шаги, потом объяснение.** Инструкция — нумерованный список действий,
  «как это работает» — после.
- **Безличный стиль:** «команда создаёт файл», а не «я сделал».
- **Строки до ~100 символов** — так удобнее читать diff.
- Списки — через `-`, перед списком — пустая строка.
- **У каждого блока кода — язык:** `sh`, `python`, `text`, `toml`, `powershell`…
- Картинки — в `docs/assets/images/`, с понятным именем.
- Ссылки внутри вики — относительные (`../start/ssh.md`), на разделы — по якорю.
  Для заголовков на русском задавайте явный якорь: `## Получение root { #root }`.
- Предупреждения — блоками MkDocs Material: `!!! warning "Заголовок"`, `!!! note`, `??? tip`.
- Новая страница модели — по образцу существующих в `docs/devices/` + строка в
  `docs/devices/index.md` и пункт в `nav` в `mkdocs.yml`.

## Скрипты и бинарники (`contrib/`)

- Скрипты для колонки — POSIX `sh` (там BusyBox, не bash); проверка `sh -n script.sh`.
- В начале скрипта — комментарий: что делает, на каких моделях проверен, как откатить.
- Бинарники — статические, с указанием архитектуры (`aarch64-linux-musl`, `armhf`) и
  источника или скрипта сборки. Опишите их в `contrib/README.md`.
- Ничего не делайте «молча» с системными разделами: перед правкой — резервная копия
  и способ вернуть как было.

## Что нельзя публиковать

- ключи из `/data/quasar/devices.json` (`server_private_key`, `secret`);
- MAC-адреса, серийные номера, `device_id`, хвосты имён хостов вида `_8F8C`;
- OAuth-токены, пароли, SSID и всё, что указывает на ваш дом.

Заменяйте на `<DEVICE_ID>`, `<REDACTED>`, `XXXX`. Перед PR просмотрите логи и дампы, которые
прикладываете.

## Сообщения коммитов

Коротко, по сути, можно по-русски или по-английски:

```text
docs(station-2): карта светодиодов LED-панели
contrib: yse — поддержка нескольких реестров .yap
```

Вопросы — в issues или в чате [@hackalice](https://t.me/hackalice).

# Станция 3 (platform `orion`)

!!! warning "Только сетевая разведка — без root"
    Ниже — то, что удалось узнать **чисто сетевыми методами**, без adb/ssh,
    без вскрытия корпуса. SoC, карта флеша, I2C-периферия, индикация —
    **неизвестны**, корпус не открывали. Если у вас есть такая колонка и вы
    готовы её разобрать — дополните страницу, см. [как это сделать](../contributing.md).

Розничное имя — **Яндекс Станция 3**. В mDNS и логах представляется как
`platform=orion` — эта платформа не входит ни в одну из уже описанных в разделе
[«Две аппаратные платформы»](index.md#две-аппаратные-платформы) (ни Amlogic/Buildroot,
ни Android, ни MediaTek/Yocto). Возможно, новое поколение на другом SoC — подтверждений
по железу пока нет.

## Идентификация

mDNS (`_yandexio._tcp.local`):

```
yandex-station-3-<deviceId>
    deviceId=<...>
    platform=orion
    cluster=yes
```

Открытые порты: `tcp/1961` (glagol). `adb` (5555), `ssh` (22/2222) — закрыты, сетевого
adb через DNS-метод получить не удалось (см. ниже).

**Точная версия прошивки** видна в открытом (нешифрованном) HTTP-заголовке при проверке
интернета на старте (см. ниже, `scbh.yandex.net`):

```
User-Agent: orion/0.13.1.36.3322101745.20250823.factory-13
```

Суффикс `.factory-13` — похоже на заводскую сборку (от 23.08.2025), то есть то, что
реально стоит на устройстве «из коробки», до первого OTA.

## glagol (порт 1961)

Токен получается стандартным публичным flow, как в
[AlexxIT/YandexStation](https://github.com/AlexxIT/YandexStation):
`oauth.mobile.yandex.net` → `quasar.yandex.net/glagol/token?device_id=...&platform=orion`.

Колонка принимает TCP+TLS handshake и держит соединение открытым при валидном токене
(невалидный — сразу `Invalid token` и закрытие). Но на команды из
реверс-инженеренного для старых платформ протокола — `softwareVersion`, `ping`,
`getVersion`, `status`, `allStates`, `getState`, `get_status` — **никакого ответа**, ни
ошибки, ни данных. Судя по всему, набор команд на `orion` другой и пока не описан.

## Сетевые обращения при активации

Сброс → мастер настройки (BLE + приложение «Дом с Алисой») → привязка аккаунта.
Снято `tcpdump` по MAC устройства, полный заход от DHCP до начала закачки обновления
(~13 секунд):

1. `scbh.yandex.net` — **обычный HTTP**, `HEAD /generate_204` → `204 No content`.
   Проверка интернета, без шифрования. User-Agent отсюда — см. выше.
2. `oauth.yandex.ru` — TLS, обмен токенами аккаунта (несколько попыток подряд).
3. `startup.mobile.yandex.net` — TLS, похоже на загрузку конфига/бутстрапа.
4. `quasar.yandex.net` — TLS, регистрация устройства (несколько заходов).
5. `report.appmetrica.yandex.net` — TLS, телеметрия.
6. `uniproxy.alice.yandex.net`, `rpc.alice.yandex.net` — TLS, голосовой backend Алисы.
7. `ext-cloudcdn-ruekt01mts-02.cdn.yandex.net` — отсюда качалось само обновление (OTA).

Содержимое TLS не видно (зашифровано) — известны только хосты, порядок, сертификаты,
объём и тайминг.

## DNS-метод не работает: certificate pinning

Проверяли классический [DNS-метод](../start/root.md#dns-unlock) — подмена DNS для
`scbh.yandex.net` / `oauth.yandex.ru` / `quasar.yandex.net` / `quasar.yandex.ru` на свой
сервер в локальной сети.

- `scbh.yandex.net` → свой сервер отдаёт настоящий `204 No content` — проверка интернета
  проходит нормально.
- `oauth.yandex.ru` / `quasar.yandex.net` → свой TLS-сервер с сертификатом:
    - **Самоподписанный сертификат** → колонка рвёт соединение с
      `tlsv1 alert unknown ca` (48), повторяет попытку 10+ раз, затем сдаётся
      («нет интернета в этой Wi-Fi сети»).
    - **Настоящий публично доверенный сертификат** (выпущен легально через Let's
      Encrypt на свой домен) → **тот же самый alert**.

Второй пункт ключевой: если бы колонка просто проверяла сертификат по обычному
публичному списку корневых CA, настоящий Let's Encrypt сертификат прошёл бы (пусть и
для «неправильного» домена — проверку совпадения имени хоста многие embedded TLS-стеки
не делают). Но отклонила оба одинаково → это **certificate pinning**: колонка ждёт
конкретно сертификат/CA Яндекса, а не просто «любой доверенный».

Подтверждено дампом трафика по MAC устройства (не телефона — специально разносили
устройства по разным сетям на время теста, чтобы не спутать источник).

**Вывод:** сетевой DNS-метод / MITM для `orion` закрыт. Для root, похоже, остаётся
только аппаратный путь (UART/флеш/дамп прошивки) — сетевых уязвимостей не нашли.

Подробнее и обсуждение — [issue #24](https://github.com/Marker284/yandex-station-extended/issues/24).

## Как дополнить

Если у вас такая колонка и вы готовы её разобрать — не хватает буквально всего:
SoC, разметка флеша, I2C-периферия, индикация, звуковой тракт. Минимальный набор — см.
[«Как дополнять вики»](../contributing.md#минимальный-набор-данных-для-новой-модели).
Если найдёте способ получить root (аппаратный или сетевой) — это будет первое для этой
платформы.

# Шифрование U-Boot, ядра и Device Tree на Amlogic

Всё, что написано здесь, проверялось и исследовалось на Станции Лайт (`yandexmicro`), но должно быть верно для всех станций на базе `Amlogic A113X`:
- Лайт (`yandexmicro`)
- Fiero Hi (`blackthorn`, партнёрская версия Лайт от DNS)
- Лайт 2 (`plum`)
- Мини (`yandexmini`)
- Мини 2 (`yandexmini_2`)
- Мини 3 (`bergamot`)
- Станция 2 (`yandexmidi`)
- Умный хаб (`saturn`)

И, возможно, даже для станций на других SoC от Amlogic (с некоторыми модификациями).

Низкоуровневые райтапы и код находятся [**на GitHub**](https://github.com/Sovenok-Hacker/yandexmicro-pwn).

## Общие факты о шифровании
Файловая система на `/` (**rootfs.ubifs** в OTA) не шифруется вообще.

Шифрование делится на два типа:
- чистый `AES-256-CBC`
- `AMLSECU` - собственный формат Amlogic

Шифрованию подвергаются:

|| Имя файла в OTA-архиве | Тип |
| --- | --- | --- |
| **Ядро Linux**  | `boot.img.encrypt` | `AMLSECU`, размер страницы на `0x24`, кол-во регионов на `0x40c`, первый регион - через одну страницу от начала |
| **Device Tree** | `dt.img.encrypt`   | Один регион `AMLSECU`, начиная с `0x20` |
| **BL2** (инициализация **NAND** и **DDR**)   | `u-boot.bin.encrypt.usb.bl2` | `AES-256-CBC` |
| **TPL/BL3** (содержит **OP-TEE** и **U-Boot**) | `u-boot.bin.encrypt.usb.tpl` | `AES-256-CBC` |

## AES-256-CBC
Ключ (общий): `9d979090f1077a06af41ef83e47e73e8e4c964970fb0e3dada24d2c2e1485d7e` \
IV - нулевой: `00000000000000000000000000000000`

!!! note "Откуда инфа?"
    Ключ прошивается на заводе и хранится в **eFuse**. \
    Его извлечение было выполнено с помощью эксплойта от **blasty** на Станции Лайт через **eQuasar**, реализация есть в репозитории.

## AMLSECU
Это сложный проприетарный формат, используемый Amlogic. Файлы, зашифрованные им, разбиваются на регионы.

На практике он обычно всего один, а `initramfs` вшит в ядро через `CONFIG_INITRAMFS_SOURCE`. В противном случае перед следующим регионом предыдущий добивается до целого кол-ва страниц.

Заголовок - первые `4` блока по `128` байт шифруются наивным `RSA` - каждый блок переводится в число и интерпретируется как отдельное сообщение.
Параметры:
- Экспонента: `e=3` (*да, такая маленькая*)
- Модуль (1024-битный):

На `0x0c` и `0xfc` должна располагаться четырёхбайтная сигнатура: `AMLC` \
Все числа в заголовке - в порядке **Little Endian**, **32**-битные.

Разбор заголовка:
| Расположение | Значение |
| --- | --- |
| `0x18`        | Размер данных (**dsz**) |
| `0x20`-`0x40` | Хэш-сумма (**SHA-256**) |
| `0x40`-`0x60` | Ключ **AES-256-CBC**    |
| `0x60`-`0x70` | IV **AES-256-CBC**      |

Содержимое извлекается весьма странным путём: \
`data[dsz:dsz+0x200] + data[0x200:dsz]`

Где:
- `data` - весь регион вместе с заголовком
- `dsz` - размер данных

Для расшифровки используется AES-256-CBC с этим ключом и IV, хэш-сумма берётся по нему же, **до расшифровки**.

!!! note "Что???"
    Такая крайне странная система с хранением первых `512` байт в конце придумана, видимо, для защиты от **TOCTOU**-атак при проверке подписи. Ну и, конечно, чтобы вынести мозг реверсерам :)

Интересные моменты:
- В названиях файлов в OTA-архивах (например, `u-boot.bin.encrypt.usb.tpl`) `usb` ничего не значит. Вероятно, это артефакт формата официального прошивальщика - `Amlogic USB Burning Tool` (отсылает к возможности прошивки по USB)
- В RSA используется крайне малая экспонента (`e=3`) и нестандартная система дополнения (padding) при подписи. Возможно, это ведёт к криптографическим уязвимостям (например, атака *Блейхенбахера* или *Копперсмита*).

# Подводные камни

Неочевидные особенности прошивок и железа Станций, на которые натыкались вживую.

## Файловая система

- **`/` только для чтения.** Правки: `mount -o remount,rw /` → правка → `sync` →
  `mount -o remount,ro /`.
- **Без `sync` правки теряются.** UBIFS держит записи в памяти; при зависании или выдёргивании
  питания только что записанный файл может исчезнуть целиком. После любых важных правок — `sync`.
- **`sync` может зависнуть**, если в ядре застрял упавший `mount` (например, после oops
  драйвера ФС). Тогда сбрасывайте конкретные файлы через `fsync` и перезагружайтесь по питанию.
- **`mount -o remount,ro /` может разово отдать `Device or resource busy`** сразу после
  правки файлов на `system` — не зависание, чистая ошибка за миллисекунды. Повтор команды
  или просто перезагрузка решают (проверено на Станции 3/orion, несколько раз).
- **Сам `mount -o remount,rw/ro /` может зависнуть в ядре (не только `sync`)** —
  наблюдалось на Станции 3 сразу после аппаратного factory reset: процесс `mount` вставал в
  `D`-состояние (`ps -o pid,stat` показывает `D`), в `wchan`/стеке — `rwsem_down_write_slowpath`
  и `__flush_work.isra.0`, ожидание rwsem. Все последующие попытки remount (в том числе из
  других сессий) встают в очередь за первой и тоже виснут; `adb reboot` тоже виснет по той же
  причине (путь перезагрузки тоже синхронизирует/перемонтирует ФС). `dmesg` при этом чист — ни
  ошибок I/O, ни повреждений ext4. **Разрешилось физическим отключением питания**, без потери
  данных: правки, записанные до зависания, и файловая система после чистой загрузки оказались
  целы. Если встретили это — проверьте `ps -o pid,stat,args | grep D` на зависший `mount` до
  попытки `adb reboot`.

## Построчная правка `launch.json`/JSON без парсера

На колонке нет `jq`/`python` «из коробки» — убирать task-объекты из
`launch.json` приходится построчно (по одному полю на строку), без
настоящего JSON-парсера. Проверка на валидность через баланс `{}`/`[]`
(как в `contrib/yandex-disable-telemetry.sh`) этого **не ловит**:

- **Висячая запятая при удалении последних элементов массива.** Если
  удаляемая задача была последней в списке `tasks`, у предыдущего элемента
  остаётся `,` перед закрывающей `]` — баланс скобок при этом не нарушен,
  но JSON становится невалидным. На Станции 3 ровно это произошло при
  удалении `begemot`/`bulbik` (они последние в `launch.json`), хотя для
  `telemetry`/`fluent-bitd` (не последние) баг не проявлялся. Проверяйте
  построчные правки JSON-массивов полноценным парсером (`python3 -m
  json.tool` на компьютере) **до** применения на устройстве — счёт скобок
  недостаточен.

## BusyBox

- нет `timeout`;
- `awk` без математики (`exp`, `log` → «Math support is not compiled in»);
- `tar` без `-z` (используйте `gunzip -c | tar -x`);
- `test -w` говорит «можно писать» даже на read-only разделе — проверяйте режим монтирования
  в `/proc/mounts`;
- `sync` не принимает аргументы;
- урезанный `lsusb` (только ID без названий) — полноценный ставится `yse install usbutils`;
- поиск процесса перебором `/proc/*/cmdline` с `tr` на каждый — сотни запусков программ и
  ~0,5 с на Станции 2; `ps -o pid,args` показывает командную строку целиком и в 20 раз быстрее.
- **самосовпадение `grep`/`ps` через `adb shell`.** Многострочная команда, отправленная одним
  вызовом `adb shell "..."`, уходит на колонку как единая строка `sh -c '...'` — и её полный
  текст попадает в `ps`/`/proc/<pid>/cmdline` **самого этого процесса**. Проверка вида
  `ps -ef | grep 'нужный паттерн'` в такой команде ложно матчит сама себя (в её же командной
  строке буквально есть искомый текст), даже если реального процесса с этим именем не
  запущено. Решение — делать проверку в отдельном вызове `adb shell`, не в том же, что ищет
  паттерн, либо сверять по более специфичному полю (`argv[0]`), не по произвольной подстроке.

## ADB

- **`adb push` не сохраняет права доступа.** Исполняемые файлы после push становятся
  `-rw-rw-rw-` (без execute-бита), а каталоги — группо-/мирозаписываемыми. Для бинарников
  нужен `chmod +x` после каждой заливки. Для демонов, которые сами проверяют права (например,
  dropbear отказывает во входе по ключу, если домашний каталог или `.ssh` доступны на запись
  кому-то кроме владельца) — нужны `chmod 700`/`600` на соответствующие файлы и каталоги,
  иначе получите молчаливый отказ без объяснения в логе. Конкретный пример —
  [персистентный SSH на Станции 3](../start/ssh.md#dropbear).

## Звук (ALSA)

- **Работающие плееры не видят правки `/etc/asound.conf`.** alsa-lib перечитывает конфиг,
  только если изменился главный `/usr/share/alsa/alsa.conf`, а `asound.conf` подключается из
  него хуком. После правки: `touch /usr/share/alsa/alsa.conf`.
- **`softvol` создаёт регулятор на карте своего выхода.** Если выход — не `card0`, появится
  второй `Master`, и кнопки громкости перестанут работать. Указывайте `card 0` в `control { }`.
- **Свой `ALSA_CONFIG_PATH` без `ctl.hw`.** `softvol` открывает регулятор как `hw:0` и в
  минимальном конфиге падает с `Invalid CTL hw:0`. Нужна строка из стандартного `alsa.conf`:
  `ctl.hw { @args [ CARD ] @args.CARD { type string default "0" } type hw card $CARD }`.
- **`Master` на Станции 2 — без шкалы в дБ.** Системный `softvol` создаёт регулятор без TLV
  (`amixer` пишет `TLV read error`), и `librespot --mixer alsa` с ним не стартует. Свой
  `softvol` с тем же именем и `count 1` дописывает шкалу; она держится до перезагрузки.

## Автозапуск и hotplug

- `mdev -d` читает `/etc/mdev.conf` один раз при старте: новые правила работают после перезапуска
  `mdev` или перезагрузки. Шаблон сравнивается с `DEVNAME` целиком, например `snd/controlC1`.
- `/sbin/hotplug` нет — события обрабатывает только демон `mdev`.

## Отладка падений

- Причина последней перезагрузки: `cat /sys/class/aml_info/reboot_reason`.
- `pstore` очищается при обычной загрузке (`S98pstore-clear`) — лог ядра ловите вживую:
  `ssh … 'cat /proc/kmsg'`.
- Логи демонов: `/data/quasar/daemons_logs/` (`maind.log`, `mediad.log`, `yiod.log` …).

## Память и ядро

- `devmem` (mmap `/dev/mem`) работает, а `read()` из `/dev/mem` возвращает 0 байт.
  `/dev/kmem` не читает образ ядра.
- Модули ядра: подпись (vermagic) у Яндекса — `4.9.y`, хотя `uname -r` = `4.9.68`. Но даже с
  правильной подписью модули из чистых исходников опасны: `struct task_struct` у Яндекса
  другая. Подробности — [USB Host → модули](../recipes/usb-host.md).

## Сеть

Сторож Wi-Fi (`wifiReseter`), проверка связи `generate_204` и запасные адреса DNS
(`DnsFallbackMap`) задаются в `quasar.cfg` — разбор в [Сети и портах](network.md). Резолвер
`unbound` колонки спрашивает DNS Яндекса (`77.88.8.x`) мимо DNS роутера, а его конфиг приходит
из облака: [откуда берётся конфиг](network.md#unbound-config).

### Станция 1 переподключается после AliceBridge { #station1-rollback }

На Станции 1 повторные обрывы вызывала незавершённая смена сети в агенте AliceBridge.
В сохранённой операции оставался откат с истёкшим сроком подтверждения.
Признаки, проверка причины и границы исправления разобраны в статье
[Wi-Fi после AliceBridge](station1-wifi-rollback.md).

### Свои сети Wi-Fi пропадают после перезагрузки { #wifi-capability }

Если дописать сеть прямо в `wpa_supplicant.conf` (или через `wpa_cli`), она проработает до
перезагрузки. При старте `maind` сверяет сети с последней Wi-Fi-директивой из облака и удаляет
лишние. В `maind.log`: `Removing network from configured, id: 5, ssid: <сеть>`. Директива
хранится в `/data/quasar/data/wifi_capability.lmdb` (`last_directive`, записи
`TWifiCapability.TNetworkInfo`).

- Штатный путь — добавить сеть через приложение «Дом с Алисой», тогда она попадёт в директиву.
- Без приложения можно дописать сеть в саму директиву в LMDB. Так делали на Мини 2, и `maind`
  принял запись с прежним хешем. База собрана с 32-битными номерами страниц, поэтому py-lmdb
  на 64-битном ПК её не открывает (`MDB_INVALID`). Сделайте копию перед правкой.
- Приоритеты и флаг `disabled` у сетей `maind` тоже переписывает. Не трогает он
  `bssid_filter` (`wpa_cli set bssid_filter <bssid> …`), так колонку можно удержать на
  конкретной точке доступа. Это пригодится, если mesh-узел плохо передаёт трафик.

### mDNS пропадает через несколько минут: IGMP snooping { #igmp }

Признак: AirPlay или Spotify Connect видно сразу после подключения колонки, потом устройство
пропадает с телефона, хотя служба работает. Счётчик iptables на входящий мультикаст
показывает 0 пакетов (даже на `224.0.0.1`), а broadcast доходит.

Причина — роутер с IGMP snooping, но без IGMP querier. Ядро отправляет Membership Report за
`224.0.0.251` только при входе в группу. Запросов никто не шлёт, поэтому через несколько минут
роутер забывает о подписке и перестаёт пересылать mDNS этому Wi-Fi-клиенту. Проводных
устройств это может не касаться; ПК в той же Wi-Fi-сети страдает так же. Настройки
`allmulti` и `promisc` на `wlan0` не помогают.

Что помогает:

- на роутере — включить IGMP querier или выключить IGMP snooping;
- на колонке — периодически (например, каждые 30 с) отправлять IGMPv2 Membership Report за
  `224.0.0.251` с raw-сокета `IPPROTO_IGMP`.

Проверено на Мини 2 со вторым способом: `atvremote scan` находит приёмник и через 6 минут
после подключения, когда без отчётов он уже пропадал.

### Свой mDNS (avahi) рядом с `maind` { #avahi }

Порт `udp 5353` занимает сам `maind --platformd`: он объявляет колонку в сети как
`yandexmicro-<серийный номер>.local` (на Лайт; префикс зависит от модели) вместе с обратной
записью для её IP. Если запустить avahi (из Entware — для AirPrint, AirPlay и т. п.) с его
настройками по умолчанию, он тоже публикует адрес колонки, видит конфликт этой обратной
записи и без конца перебирает имена: в логе `Host name conflict, retrying with <имя>-2`, `-3`…,
а сервисы то появляются в сети, то пропадают. Другое имя хоста не помогает — конфликтует
именно запись для IP.

Решение — не публиковать адреса и взять имя, которое уже объявляет `maind`; тогда записи
сервисов avahi указывают на хост, который `maind` и так разрешает. В
`/opt/etc/avahi/avahi-daemon.conf`:

```ini
[server]
host-name=yandexmicro-XXXXXXXX     # имя из avahi-resolve, без .local
use-ipv6=no

[publish]
publish-addresses=no
publish-hinfo=no
```

Имя узнайте после первого запуска avahi уже с `publish-addresses=no`:
`avahi-resolve -a <IP колонки>` (серийный номер в имени не публикуйте).
Проверено на Станции Лайт. То же поведение наблюдали на Станции 2 —
см. [issue #15](https://github.com/Marker284/yandex-station-extended/issues/15).

## Livelock `led-animator` — симптом неисправного FPGA-чипа дисплея, не общий баг

**Наблюдалось на одном конкретном устройстве Станции 3 (orion,
factory-13) с аппаратно неисправным чипом дисплея** — после переисследования
выяснилось, что это не общий баг прошивки (см. ниже «Настоящая причина»).
Сначала выглядело так: при полном отсутствии интернета, как только споттер
распознаёт **полную фразу** (не только слово активации), она уходит на
классификацию, неизбежно проваливается — и после одного-двух таких
провалов подряд один из потоков `platformd` (`led-animator`) уходит в
бесконечный CPU-луп:

- `dmesg`: `RT throttling on cpu:N ... curr:led-animator/<tid>` повторяется
  каждую секунду без остановки, `sum_runtime` растёт 1:1 с wall-clock —
  поток занимает ~100% одного ядра непрерывно.
- `/proc/<tid>/wchan` потока = `0`, стек — только `__switch_to`: поток
  реально исполняется, это CPU-спин, а не блокировка на сети/диске.
- Параллельная попытка `arecord` на устройство микрофона в этот момент
  встаёт в `D`-состояние — тот же класс зависания, что и у
  `mount -o remount,rw/ro /` после аппаратного factory reset (см. выше).
- `kill -9` на зависший процесс не помогает (ожидаемо для живого
  CPU-спина, не для D-state — сам процесс жив и отвечает на сигналы, но
  поток внутри не останавливается).
- `reboot` после срабатывания несколько раз подряд **зависал** — спасало
  только физическое отключение питания. После включения — полная
  целостность (маркеры root, OTA-disable, `launch.json` целы).

**Не вина `begemot`/`bulbik`.** Проверены все 4 комбинации (вкл/выкл по
отдельности и вместе, отдельные перезагрузки, контрольный тест с реальной
фразой на каждой) — баг воспроизводился **в каждой**, с разным подтипом
ошибки классификации (`ErrorClassifierFailed` без `begemot`,
`ErrorClassifierIrrelevant` с ним), но одинаковым исходом.

### Настоящая причина: неисправен FPGA-чип Gowin (дисплей часов на кольце)

На **втором** устройстве той же модели livelock не воспроизвёлся **ни
разу**, несмотря на агрессивный повторный тест (много фраз подряд, без
пауз). Разница нашлась не в конфиге (прошивка и `quasar.cfg` у обоих
устройств побайтово идентичны), а в железе: у проблемного устройства
FPGA-чип Gowin, рисующий цифровой дисплей-часы на кольце
(`/dev/fb1`, модуль `gowin_led_device`, device tree `ya,led_screen`), не
может загрузить свою прошивку ни на одной загрузке:

```text
gowin_led_device spi0.0: application mode number mismatch: expected=0x01, actual=0x00
gowin_led_device spi0.0: failed to fetch current firmware version: -71
gowin_led_device spi0.0: Status Code: VLD bit isn't set
gowin_led_device spi0.0: Status Code: READY bit isn't set
gowin_led_device spi0.0: Status Code: POR bit isn't set
gowin_led_device spi0.0: Erasing the FPGA SRAM was failed
gowin_led_device spi0.0: erase flash attempts = 5
gowin_led_device spi0.0: failed to update firmware: -71
```

На здоровом устройстве тот же драйвер пишет `firmware is up-to-date` и
регистрирует `fb1` без единой ошибки. Побайтовый дамп `/dev/fb1`
подтверждает: у неисправного устройства буфер **полностью нулевой**
(0 из 256 строк по 16 байт непустые), у здорового — реальный узор пикселей
цифр (27 непустых строк). Статус-биты `VLD`/`READY`/`POR` не отвечают —
похоже на проблему на уровне электроники (питание/сброс чипа или
повреждённая SPI/JTAG линия), не на несовпадение версий прошивки; это
известный класс неисправности Gowin FPGA, см., например,
[issue nand2mario/nestang#5](https://github.com/nand2mario/nestang/issues/5)
с идентичными симптомами (биты `POR`/`VLD` не устанавливаются,
перепрошивка флеша проваливается, чтение флеша даёт одни нули; там же —
подтверждённого фикса не нашли даже официальным Gowin-программатором).

Вывод: судя по всему, поток `led-animator` после провала диалога пытается
восстановить idle/clock-анимацию, то есть обратиться к этому самому
«немому» чипу (зарегистрирован в ядре, но не отвечает на уровне
протокола) — и уходит в busy-retry вместо корректной обработки ошибки.
**На здоровом железе баг не воспроизводится** — то есть похоже, что
livelock специфичен для устройств со сломанным чипом дисплея, а не общий
риск для любой Станции 3.

Заводской сброс тут не поможет: он восстанавливает `system`/`boot`/
`bootloader` на eMMC, а не отдельную флеш-память FPGA-чипа — драйвер уже
и без сброса пытается перепрошить чип на каждой загрузке и стабильно не
может. Замена чипа **не требует** предварительного программирования —
прошивка (`/lib/firmware/yandex_led_screen_fpga.bin`) лежит на самой
колонке, драйвер автоматически зальёт её в новый чип при первой загрузке
после перепайки. Восстановление текущего чипа на месте потребовало бы
внешнего JTAG-программатора (официальный Gowin programmer или
`openFPGALoader` с поддержкой GWUTX) через тестовые точки
`jtag_tck/tdi/tdo/tms/sel` на плате — без гарантии успеха.

### Что не отключается само голосовое распознавание

На части прогонов (пока чип ещё давал **некоторую** реакцию) споттер
продолжал детектировать и обрабатывать речь (несколько фраз подряд
доходили до `routeDirective ... local_audio_file_play` — локальной
озвучки «нет подключения к интернету») параллельно с зависшим потоком —
ломается в первую очередь визуальная индикация на кольце, а не сама
обработка речи. Если показалось, что повторная активация «не услышана» —
пока не доиграна предыдущая озвучка, следующая активация просто
**отменяет** её (`cancelDirective local_audio_file_play`) — это штатное
поведение (перебивание), не баг.

## TLS: пиннинга сертификатов нет

Удобно для перевода колонки на свой сервер — не нужно возиться с CA
и самоподписанными сертификатами:

- HTTP-клиент на libcurl выбирает протокол (HTTP/HTTPS) по схеме из URL;
- WebSocket-клиент на websocketpp собран с двумя бэкендами — `asio_client` (чистый TCP) и
  `asio_tls_client` (TLS); схема выбирается по URI (`ws://` или `wss://`).

Поэтому в `quasar.cfg` можно прописать незашифрованные адреса для `backendUrl` (HTTP) и
`uniProxyUrl` (WS) — и колонка пойдёт по ним без проверки сертификата. Это основа подмены
бэкенда и [uniproxy](voice.md) на свой сервер.

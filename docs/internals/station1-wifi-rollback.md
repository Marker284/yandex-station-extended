# Почему Станция 1 переподключается к Wi-Fi после AliceBridge

На Станции 1 зависшая смена домашней сети в агенте AliceBridge вызывала повторные
переподключения. Доступ к серверам Яндекса при этом сохранялся между обрывами.

**Проверено на:** Станция 1 (`tulip-d1`), Android `6.0.1`, сборка
`MOB30J.20261013`, Quasar `2.369.5.46.4778391386.20261013.52`.
Агент AliceBridge — `1.0.2`, build `3`. Данные сняты через root SSH и ADB;
проверка связи дополнительно разобрана по коду установленного APK.

!!! abstract "Причина — незавершённый откат сети"
    Агент сохранял операцию со статусом `rolling_back` и истёкшим сроком
    подтверждения. После завершения этой операции переподключения прекратились.
    Приложение Quasar и его проверка связи остались без изменений.

## Как проявляется { #symptoms }

Колонка подключается к домашней сети, получает адрес и некоторое время работает.
Примерно через 40–50 секунд связь прерывается, затем подключение повторяется.
В журнале Quasar появляются две строки:

```text
WI-FI connectivity check failed
Wifi status changed to NOT_CONNECTED
```

Публичные серверы Яндекса отвечают между обрывами. Проверка ICMP до
quasar.yandex.net проходит, DNS из DHCP доступен. Само сообщение Quasar не
показывает, кто переключает сеть: приложение, Android или установленный помощник.

На этой Станции параллельно запускался процесс с классом
`dev.alice.station.StationWifi` и операцией `switch`. Его родителем был агент
AliceBridge. Приложение на телефоне для повторного запуска не требовалось.

## Что осталось после смены сети { #transaction }

Агент хранит состояние в `/data/quasar/alicebridge-agent/config.json`.
В нём обнаружилась операция, срок подтверждения которой истёк более трёх суток назад.
К моменту диагностики агент по-прежнему показывал незавершённый откат.
Сокращённый ответ его команды состояния выглядел так:

```json
{
  "home_configured": false,
  "wifi": { "connected": true },
  "transaction": {
    "phase": "rolling_back",
    "message": "Wi-Fi confirmation timed out"
  }
}
```

Целевая сеть в операции совпадала с текущей домашней сетью. Предыдущая сеть была
точкой AliceBridge. Получилось противоречивое состояние: колонка уже подключена
куда нужно, но агент не считает переход завершённым и продолжает откат.

Владелец заметил первый обрыв при переходе с точки AliceBridge на домашний Wi-Fi.
Это согласуется с истёкшим подтверждением. Однако журнал самого первого обрыва
при разборе не был доступен: нельзя установить, почему не пришло подтверждение и была ли
предыдущая точка доступна во время каждой попытки отката.

## Почему проверка DNS увела в сторону { #dns }

В resolv.conf оставался частный адрес 10.99.195.164, хотя DHCP выдавал другие
DNS-серверы. Файл оказался ссылкой на
`/data/opt/etc/alicebridge-resolv.conf`, а не обычным результатом DHCP.

Недоступный адрес заменили на выданные роутером DNS Яндекса. Разрешение имён
проверили, но переподключения продолжились. Поэтому неверный DNS был отдельной
найденной настройкой, а не достаточным объяснением цикла.

Наблюдение сокета процесса ping с адресом и портом 1025 тоже не доказывает,
что именно туда отправляется проверка Quasar. Назначение этого сокета отдельно
не установлено; передача UDP-пакетов на этот порт захватом не подтверждена.

Описанный в разделе [Сеть и порты](network.md#dns-unbound) резолвер unbound
проверялся на других моделях. На этой Android-Станции работающий процесс unbound
не обнаружен. Переносить всю ту схему на Станцию 1 без проверки нельзя.

## Что проверяет Quasar { #connectivity-check }

В установленном APK класс ConnectivityChecker вызывает ConnectionProber.
Тот выполняет HTTP HEAD и признаёт успехом только код ответа 204.
По умолчанию адрес собирается из robotBackendHost и пути /generate_204;
полученная приложением конфигурация может переопределить адрес и таймаут.

В локальном конфиге этой Станции указан scbh.yandex.net. Запрос к его
/generate_204 возвращал 204 и от root, и при отдельном запуске клиента с UID
Quasar и группой Android, разрешающей доступ к сети. Значит, доступ к контрольному
серверу вне работающего процесса приложения был исправен. Этот тест сам по себе
не раскрывает фактические настройки каждого запроса внутри Quasar.

Успешный ping проверяет ICMP. Ответ HTTP 200 подтверждает доступность сервера,
но не удовлетворяет найденному условию Quasar. Для этого нужен именно 204.

Ещё одна строка журнала — Wifi alternate reality enabled — оказалась штатной
частью Android. В [исходнике WifiManager][android-wifi] она сопровождает выбор
Wi-Fi-сети для процесса. Эта строка сама по себе не означает подмену DNS.

[android-wifi]: https://android.googlesource.com/platform/frameworks/base/+/3e7d977/wifi/java/android/net/wifi/WifiManager.java

## Как установили источник переподключений { #isolation }

Замена DNS не прекратила обрывы. Перезапуск одного Quasar тоже не помог.
Затем агент AliceBridge временно приостановили на 90 секунд, а его точно
определённый помощник переключения сети завершили. Возобновление агента было
запланировано заранее.

Во время паузы новые ошибки проверки не появлялись, подключение сохранялось.
После автоматического возобновления агента ошибки и переподключения вернулись.
Вместе с сохранённой операцией отката и повторным запуском помощника это
указывает на агент как источник цикла в проверенном случае.

Строка WI-FI connectivity check failed была следствием или сопутствующим признаком
этого цикла. Сам момент отказа HTTP-запроса внутри приложения не перехватывался.
Причину первоначального обрыва при смене сети этот опыт не устанавливает.

## Что изменили { #repair }

Перед исправлением сохранили исходную конфигурацию агента и DNS-файл.
Домашней сетью назначили уже подключённую целевую сеть из сохранённой операции.
Операцию перевели в завершённое состояние, затем перезапустили агент
с переменными окружения Android. Имя сети и пароль сохранились.

После исправления агент показывал настроенную домашнюю сеть и состояние
операции `committed`. Повторный запуск помощника с операцией переключения
прекратился. APK Quasar, quasar.cfg, настройки роутера и прошивку не меняли.

Это восстановление конкретного сохранённого состояния, а не универсальная
команда для любого обрыва Wi-Fi. В проверенной версии обычное подтверждение
не предназначено для уже просроченной операции отката. Подмена состояния без
сверки текущей и целевой сетей может закрепить другую сеть.

## Что проверено после исправления { #verification }

При первой проверке спустя несколько минут после исправления новых ошибок
проверки и переподключений не было. HTTP HEAD к контрольному адресу возвращал 204;
SSH и ADB с компьютера работали.

Повторная проверка спустя почти шесть часов также не выявила возврата проблемы.
Доступный журнал охватывал около четырёх последних часов: в нём не было ошибок
проверки связи и переподключений. Агент видел домашнюю сеть и завершённую операцию.
В коротком тесте все 15 запросов ping получили ответ, HTTP-проверка вернула 204.

За отдельный двухминутный тест получено 120 ответов ping из 121 запроса.
Потерян один пакет, около 0,83%; это не нулевая потеря.

Станцию не перезагружали. Конфигурация записана на раздел данных, но сохранение
результата после перезагрузки не проверялось. Непрерывного наблюдения за все шесть
часов не было; проверки выполнены сразу после исправления и при повторном подключении.

Сразу после исправления индикатор ADB внутри агента показывал unavailable
при работающем ADB с компьютера. Спустя почти шесть часов агент показывал ready
для ADB и SSH. Причина первоначального расхождения отдельно не разобрана.

## Что это значит на практике { #practice }

Если обрывы начались после смены сети через AliceBridge, полезно проверить
незавершённую операцию агента прежде, чем отключать проверку связи Quasar.
Совпадение симптомов без такой операции ещё не означает ту же причину.

Настройка домашнего Wi-Fi описана в [гайде AliceBridge](../start/root-android.md).
Общие пути восстановления собраны в разделе
[Если что-то сломалось](../start/recovery.md).

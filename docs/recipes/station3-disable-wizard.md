# Отключение begemot/bulbik на Станции 3 { #station3-disable-wizard }

Рецепт останавливает две роли, не связанные с телеметрией, но такие же
бесполезные без облака: `begemot` (поисковый wizard — мгновенные ответы:
погода, калькулятор) и `bulbik` (сценарии умного дома). Общее устройство
ролей `maind`/`launch.json` разобрано в [Как это устроено](../internals/architecture.md#launch-json);
про отдельные бинарники `begemot`/`bulbik` на Orion — на
[странице модели](../devices/station-3.md#differences).

**Проверено на:** Станция 3 (orion), прошивка `factory-13`
(`0.13.1.36.3322101745.20250823`), **два физических устройства**, root
([DNS-метод](../start/root.md)), телеметрия и обновления уже отключены
([отключение телеметрии](station3-disable-telemetry.md),
[`yandex-noupdate.sh`](../start/ssh.md#kill-ota)). Проверены применение,
перезагрузка и откат.

!!! info "Зачем — bulbik не локальный хелпер"
    `bulbik` — 258MB Go-бинарник. `strings` по нему находит буквально кусок
    серверного кода Яндекса: строки `NAlice.NMegamind` (облачный «мозг»
    сценариев умного дома), захардкоженные URL
    `iot.quasar.yasmina.yango.com`, `market.yandex.ru/...`,
    `avatars.mds.yandex.net/get-iot/...`, embedded клиент YDB и grpc. Это не
    локальная логика, а серверный код, скомпилированный под ARM и
    запускаемый на устройстве для связи с облаком — без интернета он не
    может выполнять свою функцию вообще. На живой колонке (до отключения)
    `netstat` показал **ноль** established-соединений на локальном порту
    `bulbik` (`9337`) и `begemot` (`9322`) — то есть оба просто простаивали
    в памяти.

## Шаги { #steps }

1. Скопируйте скрипт на колонку и запустите:

    ```sh
    adb push contrib/yandex-disable-wizard.sh /data/opt/yandex-disable-wizard.sh
    adb shell sh /data/opt/yandex-disable-wizard.sh
    adb shell reboot
    ```

2. После перезагрузки проверьте:

    ```sh
    adb shell sh /data/opt/yandex-disable-wizard.sh status
    ```

    ```text
    == статус begemot/bulbik ==
    launch.json : begemot убран
    launch.json : bulbik убран
    -- процессы:
       begemot не запущен
       bulbik не запущен
    ```

## Откат { #rollback }

```sh
adb shell sh /data/opt/yandex-disable-wizard.sh restore
adb shell reboot
```

!!! warning "Бэкап лежит на колонке и пропадёт при сбросе"
    Оригинал сохраняется в `/data/opt/backup/launch.json.orig-pre-wizard` —
    отдельно от бэкапа `yandex-disable-telemetry.sh`
    (`launch.json.orig-pre-telemetry`/`launch.json.orig`), так что откат
    этого слоя не трогает решение по телеметрии и наоборот. Забирайте бэкап
    к себе сразу после применения (`adb pull /data/opt/backup ./backup-колонки`).

## Как это работает { #how-it-works }

- Как и `telemetry`/`fluent-bitd`, роли `begemot`/`bulbik` запускает
  `quasar_launcher2` по списку задач из `launch.json`. Убрав их task-блоки,
  лаунчер просто не запускает эти роли.
- Остальные роли (`platformd`, `mediad`) штатно переживают их отсутствие:
  после отключения на обоих устройствах `maind.log`/`mediad.log` не
  содержат **ни одного** упоминания begemot/bulbik — платформа даже не
  пытается к ним обращаться без явного запроса (в отличие от телеметрии,
  которая обращается к `metricad` непрерывно и после отключения оставляет
  периодические warning о таймауте).
- Освобождает ~250MB RSS: `begemot` ~123MB, `bulbik` ~90MB, его отдельный
  логгер (`maind --loggerd bulbik`) ~37MB.

!!! tip "Побочный эффект отключения телеметрии: лог-спам bulbik"
    Если `bulbik` ещё жив, а телеметрия уже отключена — его логгер
    (`maind --loggerd bulbik`) каждые ~10 секунд, бесконечно, пишет в
    `bulbik.log` warning о недостижимости `metricad`
    (`metrica_connector.cpp:519`). Не критично (как и
    [аналогичный шум у других ролей](../internals/telemetry.md#disable)),
    но лишняя причина убрать `bulbik` целиком, если он не нужен.

## LED-кольцо: проверка регрессии { #led-check }

!!! warning "bulbik формально отвечает за кольцо Алисы — но это не вся правда"
    [Страница модели](../devices/station-3.md#led) описывает кольцо через
    LED-триггер `ledfb-ring` и упоминает, что оверлей громкости поверх
    кольца рисует именно `bulbik`. Это выглядело как реальный риск сломать
    визуальную индикацию на физических кнопках, отключив роль целиком.

    Удалённая проверка (`amixer set Master N%`, в том числе с `bulbik`,
    временно поднятым вручную на штатном порту `9337`, не через
    `launch.json`) ничего не показала: `/dev/fb2` не менялся, в логе
    `bulbik` не появилось ни одного входящего запроса — оверлей не слушает
    смену громкости в ALSA напрямую, этим способом регрессию не поймать.

    **Физическая проверка на обеих колонках** (реальные нажатия кнопок на
    корпусе после отключения `bulbik`) показала: mute, свайп по кольцу
    громкости, переключение ambient-подсветки и кнопка `activate`
    (play/pause, см. ниже) — **вся визуальная индикация работает как
    обычно**. Похоже,
    базовая LED-реакция на физические кнопки обрабатывается
    `platformd`/ядерным LED-классом напрямую, а `bulbik` нужен только для
    более сложных облачных сценариев оверлея (которые и так недоступны без
    интернета). Проверка со звуком (mute и микрофон реальны, не только
    LED) — в блоке ниже.

!!! success "Проверка со звуком сделана — микрофон и mute реальны, не только LED"
    Живой тест подтвердил: реальная произнесённая фраза доходит до
    микрофона и распознаётся локально (`local_recognizer.cpp:
    LocalRecognizedPhrase`, текст совпал со сказанным слово в слово) — см.
    [«Исключение на Станции 3» в Голосовом тракте](../internals/voice.md).
    Кнопка mute действительно отключает приём с микрофонов на уровне
    прошивки (`event_loop_audio_device_input_controller.cpp: Mute/Unmute
    microphones`, лог `platformd`), а не только гасит индикатор — это
    отдельный программный контроллер, срабатывающий от кнопки напрямую,
    без облака. Громкость при свайпе по кольцу тоже меняется реально, не
    только визуально — подтверждено на слух.

!!! bug "Кнопка `activate` — это play/pause, не «начать диалог», и кольцо не слушает"
    Единственная физическая кнопка верхней панели (`ButtonIdx 0`, событие
    `activate` в `buttons_handler.cpp`) ожидалась как «кнопка начала
    диалога с Алисой» — на деле это **play/pause**
    (`buttons_actions.cpp: Toggle play/pause`). Живой тест: нажали кнопку
    без играющей музыки → `playback_control_capability.cpp: Request music
    as no player is active` → `alice_request.music_play_semantic_frame`
    (текстовый запрос `Vins.TextInput`, **не голосовой**) → кольцо уходит
    в анимацию `alice_thinking.led` и держит её **15 секунд** (таймаут
    `Vins request timeout elapsed: 15000 ms`, тот же паттерн, что у
    фоновых запросов геолокации) → падает в локальную озвучку «нет
    подключения к интернету» → кольцо возвращается в idle.

    Всё это время (все 15 секунд) в логе **нет** `onAliceStateChanged:
    LISTENING` и ни одного события `local_recognizer` — микрофон не
    слушает, несмотря на анимацию «thinking». Фраза, сказанная в это
    окно, никуда не записывается и не распознаётся. Отдельный код клавиши
    `KEY_VOICECOMMAND` (582, см. [«Вход»](../devices/station-3.md#input))
    существует в системе отдельно от `activate` — настоящая голосовая
    активация кнопкой (если это другой жест, не единичный клик) **не
    проверена**.

!!! danger "Отдельный найденный баг — похоже на неисправность конкретного устройства, не регрессия"
    При дальнейшей проверке найден livelock потока `led-animator` внутри
    `platformd` на одном из двух проверенных устройств — кольцо зависало
    после нескольких провалившихся голосовых диалогов (нет сети вообще).
    Проверены все 4 комбинации `begemot`/`bulbik` — баг воспроизводился в
    каждой, значит отключение этих ролей тут ни при чём. Но дальнейшее
    расследование нашло более вероятную причину: у этого конкретного
    устройства аппаратно неисправен FPGA-чип дисплея часов на кольце
    (`gowin_led_device`, `/dev/fb1`) — не грузит прошивку ни на одной
    загрузке. На **втором** устройстве с исправным чипом баг не
    воспроизвёлся ни разу, даже при агрессивном тесте. Подробности,
    признаки неисправности чипа и восстановление —
    в [«Подводных камнях»](../internals/gotchas.md).

## Ограничения { #limits }

- Как и для [отключения телеметрии](station3-disable-telemetry.md#limits),
  после правки `mount -o remount,ro /` может разово отдать `Device or
  resource busy` без зависания — перезагрузка решает.
- Не проверялось на других моделях — `begemot`/`bulbik` как отдельные
  бинарники (не симлинки на `maind`) специфичны для Orion, см.
  [«Чем отличается»](../devices/station-3.md#differences).
- LED-проверка (выше) дополнена тестом со звуком: mute, громкость и
  микрофон подтверждены реальными «под капотом» (не только LED). Кнопка
  `activate` (play/pause) при этом **не активирует** прослушивание — см.
  предупреждение выше.

## Найденные по пути баги в самой технике удаления задач { #bugs-found }

Оба скрипта (`yandex-disable-telemetry.sh` и `yandex-disable-wizard.sh`)
убирают task-объект из `launch.json` построчно, по одному полю на строку —
без полноценного JSON-парсера (на колонке его нет). При подготовке этого
рецепта нашлись два слабых места такого подхода:

1. **Висячая запятая при удалении последних элементов массива.** Проверка
   `json_ok` считает только баланс `{}`/`[]` — этого достаточно, пока
   удаляемая задача не последняя в списке `tasks`. У `begemot`/`bulbik` на
   Orion это ровно тот случай: оба — последние два элемента, и после их
   удаления у предыдущей задачи (`maind --platformd`) остаётся запятая
   перед закрывающей `]`, из-за которой `launch.json` становится
   невалидным JSON, хотя баланс скобок не нарушен. Пойман до применения на
   устройстве — локальным dry-run с `python3 -m json.tool`. Добавлен
   отдельный проход `fix_trailing_commas`, который чистит такие запятые;
   backported и в `yandex-disable-telemetry.sh`.
2. **Самосовпадение `grep`/`ps`** (см. общее описание капкана в
   [«Подводные камни»](../internals/gotchas.md)) — в первой версии
   `do_status` нового скрипта паттерн `"/bulbik/bulbik "` совпадал с
   командной строкой самого `grep`, выдавая ложное «РАБОТАЕТ» даже когда
   процесса не было. Исправлено тем же приёмом, что уже использован в
   `yandex-disable-telemetry.sh` (`[-]-$t`) — здесь в варианте `[b]ulbik`.

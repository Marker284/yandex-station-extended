# Станция Макс — ADB Max

Root shell на Яндекс Станции Макс (`yandexstation_2`, YNDX-0008) без правки
прошивки и без записи на блочные устройства. Единственное, что нужно на
старте, — сетевой ADB.

```
uid=0(root) gid=0(root) groups=0(root) context=u:r:kernel:s0
```

!!! warning "Только для своей колонки"
    Утилита получения доступа на время исполнения перезаписывает двенадцать слов kernel text и
    переводит SELinux в permissive. Падение посреди прогона оставляет колонку
    в неисправном состоянии. Читайте [«Подводные камни»](#подводные-камни)
    перед первым запуском.

!!! danger "Это не DNS-метод"
    [DNS-метод](root.md) на Максе **не работает**: это Android-платформа
    (YaOS_X, Android 9), `adbd` здесь production и `adb root` отвечает
    `adbd cannot run as root in production builds`. Дерева
    `/system/vendor/quasar/`, скрипта `activate_adb.sh` и `onboot.sh`, на
    которые опирается DNS-метод, на Максе нет.

    Здесь описан другой путь — локальная эскалация привилегий.

Инструмент и полное описание метода получения доступа — в репозитории[^repo].

[^repo]: <https://github.com/amirilivice/yandex-station-2-s905x2-root>

---

## Что понадобится

- колонка на прошивке **`PPR1.180610.011.20220415`**, ядро `4.9.113-g985a1e6b`;
- сетевой ADB до колонки;
- компьютер с `adb`;
- **Android NDK** (использовался r26d) и Python 3 — для сборки payload.

Прошивку **не обновляйте** до и во время работы: обновление меняет ядро и все
адреса для получения доступа становятся неверными.

---

## 1. Проверьте прошивку

Все константы привязаны к одной сборке ядра. На другой сборке payload
перезапишет не те слова kernel text, поэтому проверяем первым делом:

```sh
adb shell getprop ro.build.fingerprint
```

Ожидается:

```
Yandex/yandexstation_2/yandexstation_2:9/PPR1.180610.011/20220415:user/release-keys
```

Если fingerprint другой — **остановитесь**. Константы придётся пересчитывать из
образа ядра этой сборки; как это делается, описано в репозитории.

Заодно снимите состояние — оно подтверждает, что вы на нужной платформе:

```sh
adb shell getprop ro.product.device      # yandexstation_2
adb shell uname -a                        # 4.9.113-g985a1e6b
adb shell id                              # uid=2000(shell)
adb shell getenforce                      # Enforcing
```

---

## 2. Получите сетевой ADB

Получение доступа стартует из `uid=2000(shell)` — больше от ADB ничего не требуется.
Root по ADB на Максе не выдаётся, и это ожидаемо.

```sh
adb connect <IP-колонки>:5555
adb devices          # должно быть:  <IP-колонки>:5555    device
adb shell id         # uid=2000(shell) ... context=u:r:shell:s0
```

Два момента про это состояние:

- **`/data/local/tmp` доступен на запись**, `/tmp` — нет. Работаем через
  первый.
- **`dmesg` закрыт** (`kernel.dmesg_restrict`), многие узлы `/proc` и `/sys`
  отвечают `Permission denied`. Это нормально и как раз поэтому нужна
  эскалация.

---

## 3. Соберите payload

```sh
git clone https://github.com/amirilivice/yandex-station-2-s905x2-root
cd yandex-station-2-s905x2-root
python tools/build.py /path/to/android-ndk-r26d
```

Скрипт находит `armv7a-linux-androideabi21-clang.cmd` внутри NDK и собирает
`src/reader4.c` с `-O2 -fPIE -pie -DSHELL`. Готовый бинарник — `src/reader4`.

Две оговорки по сборке:

- `-static` с этим тулчейном не линкуется;
- `-DSHELL` обязателен.

Что именно выполнится от root, задаётся **на этапе сборки**, потому что команда
зашивается в бинарник:

```sh
python tools/build.py /path/to/ndk \
    --payload "id > /data/local/tmp/who.txt; getenforce >> /data/local/tmp/who.txt"
```

Без `--payload` берётся безопасная команда по умолчанию: `id`, `getenforce`,
список `/dev/snd/` и возврат SELinux в enforcing.

---

## 4. Запустите

Скриптом — он сам проверит `uptime`, зальёт бинарник, сверит md5 на устройстве
и покажет хвост лога:

```sh
python tools/build.py /path/to/android-ndk-r26d --device --serial <IP-колонки>:5555
```

Вручную — обратите внимание, что `rm`, запуск и чтение лога идут **одной
командой**: колонка может перезагрузиться между отдельными командами, и тогда
в `/data/local/tmp/r4.log` останется лог предыдущего прогона.

```sh
adb push src/reader4 /data/local/tmp/reader4
adb shell "md5sum /data/local/tmp/reader4"     # сверить с локальной копией
adb shell "chmod 755 /data/local/tmp/reader4"
adb shell "rm -f /data/local/tmp/r4.log; \
  timeout 240 /data/local/tmp/reader4 > /data/local/tmp/r4.log 2>&1; \
  echo RUN_DONE; id; getenforce"
```

**Перед каждым запуском проверяйте `uptime`** — колонка перезагружается
самостоятельно, `/data/local/tmp` при этом очищается, а лог от прошлого прогона
переживает перезагрузку и легко принять его за свежий. Uptime должен быть не
меньше трёх минут.

**Запускать нужно один раз.** Каждый прогон пишет `0` в `selinux_enforcing` и
меняет двенадцать слов `sel_read_checkreqprot`; повторный запуск без
перезагрузки не рекомендуется.

## 5. Результат

```sh
adb shell cat /data/local/tmp/r4.log
```

Признак успеха — `id` из процесса, который payload запустил уже после
эскалации:

```
uid=0(root) gid=0(root) groups=0(root) context=u:r:kernel:s0
```

**Проверять root надо обязательно в новом процессе.** bionic кэширует
`getuid()`/`geteuid()` при старте процесса, поэтому внутри того же процесса,
который читал узел, проверка ничего не покажет. Именно поэтому payload
завершается через `execl("/system/bin/sh", "sh", "-c", payload, ...)`.

### Если не получилось

- **`EXIT_STATUS=139` или `138`** — SIGSEGV/SIGBUS, гонка за раскладку памяти
  проиграна. Перезагрузите и попробуйте снова.
- **`RUN_DONE` не напечатался, процесс в состоянии `R 0`** — завис.
  `adb reboot`, затем подождать 70 с, потом ещё 150 с.
- **Код возврата 255** — колонка перезагрузилась во время команды.
- **`push` написал `error: closed`** — заливка молча не прошла. Поэтому md5
  сверяется на устройстве, а не только локально.

## Что можно сделать с полученным root

Root выдаётся **одному процессу**, а не демону: как только он завершится,
следующий процесс снова будет `uid=2000(shell)`. Постоянного шелла, `su` или
изменённого `adbd` здесь нет. Всё, что нужно снять с колонки, нужно делать
**внутри команды payload**, в том же прогоне.

Полезно помнить, что процесс работает в домене `u:r:kernel:s0`, поэтому ему
доступно то, что закрыто для `shell`: `/proc/kallsyms` (пригодится при переносе
метода получения доступа на другую сборку), `/proc/config.gz`, блочные устройства.

**Чего root здесь не даёт:**

- **`/system`, `/vendor` и `/` не смонтировать на запись с сохранением
  изменений.** AVB 1.1 и dm-verity работают ниже того интерфейса, через который
  этот метод даёт доступ, и правка системного раздела ломает проверку целостности.
- **Постоянного доступа нет** — привилегия живёт ровно один процесс.

Это исследовательский примитив, а не jailbreak.

## Возврат в исходное состояние

Процесс получения доступа **ничего не пишет на диск и не меняет прошивку**, поэтому перезагрузка
возвращает колонку в прежнее состояние.

```sh
adb shell getenforce          # должно быть Enforcing
```

Если напечатало `Permissive` — вернуть принудительный режим можно и без
перезагрузки, из root-прогона:

```sh
echo 1 > /sys/fs/selinux/enforce
```

Перезагрузка нужна для другого — она восстанавливает двенадцать слов kernel
text, которые перезаписал прогон.

Уберите за собой:

```sh
adb shell rm -f /data/local/tmp/reader4 /data/local/tmp/r4.log
```

Всё ниже — наблюдавшиеся отказы, а не теория. Подробный разбор с версиями

## Как это работает

Колонка закрыта AVB 1.1, dm-verity на `/vendor` и `/`, SELinux в режиме
enforcing и production-сборкой `adbd`. Правка rootfs недоступна, поэтому путь
внутрь — локальная эскалация в ядре.

Уязвимость — use-after-free в драйвере Mali GPU (`kbase`). Драйвер
отдаёт userspace `mem_handle` на страницу, которую продолжает использовать для
своих таблиц страниц уже после освобождения. Освобождённая страница
переиспользуется как таблица страниц для GPU-адреса, и через неё userspace
получает доступ на запись к произвольной физической странице памяти ядра.
Утилита получения доступа пользуется этим дважды: сначала ослабляет SELinux, затем записывает
шеллкод, вызывающий `commit_creds(init_cred)`.

Читать узел `/sys/fs/selinux/checkreqprot` достаточно, чтобы сработал хук —
отсюда и формулировка «root одним `read()`».

Целевые параметры этой сборки:

| Константа | Значение | Что это |
|---|---|---|
| `YNDX_INIT_CRED` | `0x164b268` | `init_cred` |
| `YNDX_COMMIT_CREDS` | `0x4c1e0` | `commit_creds` |
| `YNDX_SEL_READ_ANCHOR` | `0x36c578` | `sel_read_checkreqprot` |
| `YNDX_SELINUX_ENFORCING` | `0x189352c` | `selinux_enforcing` |
| `KERNEL_BASE` | `0x1080000` | адрес загрузки |

KASLR на этой сборке отключён. Адрес загрузки независимо подтверждён по дампу
раздела `boot`, снятому с самой колонки.

## Отличия от DNS-метода

| | [DNS-метод](root.md) | Этот способ |
|---|---|---|
| Модели | Лайт, Мини, Миди, Станция 2 | **Станция Макс (YNDX-0008)** |
| Платформа | Buildroot / quasar | **Android 9 (YaOS_X)** |
| Механизм | ответ активации `adbd.remoteActivation=true` | **use-after-free в драйвере Mali** |
| Результат | `adbd` на `:5555` от root, постоянно | root на **одном процессе** |
| Сброс к заводским | **обязателен** | не нужен |
| Правка прошивки | маркеры в `/data/quasar` | **никакой** |
| Живёт после перезагрузки | да | нет |

Инструмент, полное описание получения доступа и разбор портирования на другую сборку
ядра — в том же репозитории[^repo].

    Закрепить SSH на Мини 3 Про factory-12¶

    Для опытного владельца с уже подтверждённым root: SSH только по ключу, без сетевого ADB и штатного OTA, с сохранением Quasar. Это ручной проверяемый порядок, не установщик.

    Проверено на: Yandex Pickle EVT, 0.12.1.8.2901568369.20250228.factory-12, 15 ноября 2026 года. Далее эта сборка обозначена как .8.

    Сброс стирает данные, перепрошивка может убрать доступ

    Сброс может удалить Wi-Fi, привязку и ключи. На проверенной колонке физический сброс восстановил резидентную .8; программный factory_reset лишь перезагрузил retail. Это не универсальный откат с .50. Используйте процедуру производителя именно для своей модели, не команды записи разделов или переменные загрузчика от другой колонки.

    Что понадобится¶

    • Своя Мини 3 Про с проверенной .8, root-оболочка через DNS-метод.
    • ПК с Python 3, POSIX sh, OpenSSH и ADB; управляемые DNS/DHCP и изоляция WAN колонки.
    • Проверенный свой сервер обновлений, без выдачи прошивок: ответ hasUpdate:false, запрет архивов, доступ только из нужной локальной сети.
    • Отдельный клиентский ключ SSH, совместимые Dropbear и dropbearkey, локальные копии оригиналов с контрольными суммами, владельцами и правами. Не публикуйте эти копии.

    Не ставьте общий скрипт блокировки OTA поверх этого порядка: здесь не меняются CA, ключ проверки OTA, загрузчик, окружение загрузки и штатный запуск Quasar.

    Подтвердите исходное состояние¶

    1. Сохраните настройки DNS/DHCP и точные правила, которые будете менять. Ограничьте WAN только этой колонки, включая IPv6, сохранив LAN, DHCP, DNS и NTP. Ограничьте доступ к сетевому ADB компьютером настройки; не считайте непроверенный Wi-Fi путь между клиентами отфильтрованным. Не перезагружайте роутер с временными правилами.
    2. Проверьте локальный сервер: TLS, ответ без обновления, запрет архивов и область доступа. Не проксируйте учётные данные и не устанавливайте новый CA на колонку. Проверка сервера с ПК ещё не доказывает, что колонка приняла его TLS или открыла ADB.
    3. Получите root по указанному DNS-методу. Если нужен сброс, отдельно согласуйте потерю данных; настройте колонку настоящим приложением, не старой записью звука привязки.

    4. Прочитайте UID, модель, версию и монтирования из реальной оболочки:

      id -u
cat /proc/device-tree/model
cat /system/vendor/quasar/version_full
cat /proc/mounts

    5. Сверьте .8, UID 0 и UBIFS для корня, исходно только для чтения. Не определяйте версию по User-Agent. При другой сборке остановитесь: этот порядок её не проверял. Приватно зафиксируйте идентификатор загрузки для последующей проверки перезагрузки.

    Если изоляция WAN мешает привязке, не открывайте весь интернет. В конфигурации .8 авторизация обращается к login.yandex.ru, mobileproxy.passport.yandex.net и oauth.yandex.ru. В проверенной настройке временно разрешены только свежие IPv4 этих имён на TCP 443, без пересечения с известными адресами обновлений; остальная блокировка сохранена. Это снимок DNS-ответов, не фильтр по имени сервера: общие или изменившиеся адреса требуют новой проверки. Учётные данные идут напрямую по штатному TLS, не через сервер настройки. Само исключение не доказано как единственная причина получения root.

    Подготовьте SSH только по ключу¶

    1. Проверьте ABI и справку именно выбранного бинарника. На .8 штатные программы — ELF64 AArch64, ядро имеет CONFIG_COMPAT=y; проверенный статический ARM32 Dropbear 2026.94 действительно запускался. Одного uname -m недостаточно.

    2. Сверьте источник и SHA-256 бинарников. Проверены исторические community-бинарники Marker284/yandex-station-extended из contrib/bin; текущий каталог бинарников не означает те же байты, ABI или ключи командной строки.

      Файл Git blob SHA-256
      dropbear 287d98332223dc5267fb939fe6c1f84b31a66f6d 374be9f85dabfab4d1f649d553f45e6238973e272b447fd2d81c2ab24a654db2
      dropbearkey 2df0d46ab5afd2dd7951e19d88c4cac63dbb67b2 86dee7ca66376f9ff463dd3d455e8f248239becdeb46ea8f71886ef1eaa4d3e7

      Из полного клона репозитория вики сохраните именно эти объекты и проверьте суммы:

      git cat-file blob 287d98332223dc5267fb939fe6c1f84b31a66f6d > dropbear
git cat-file blob 2df0d46ab5afd2dd7951e19d88c4cac63dbb67b2 > dropbearkey
sha256sum dropbear dropbearkey

    3. Разместите проверенный Dropbear в /data/opt/bin/dropbear, генератор — рядом. Задайте исполняемые права 0755 и владельца root. Создайте каталог /data/opt/etc/dropbear с правами 0700. Если пути уже заняты, сначала разберите существующую установку, не перезаписывайте её.

    4. Сгенерируйте Ed25519 host key на колонке в /data/opt/etc/dropbear/hk_ed25519. Передайте только публичный клиентский ключ в /data/opt/etc/dropbear/authorized_keys; задайте обоим файлам 0600 и root. Приватный клиентский ключ остаётся на ПК, приватный host key — на колонке.

      Если host key ещё отсутствует, создайте его на колонке:

      umask 077
/data/opt/bin/dropbearkey -t ed25519 -f /data/opt/etc/dropbear/hk_ed25519
      5. Подтвердите публичный host key через уже проверенную root-оболочку. Закрепите его в отдельном known_hosts на ПК. Не принимайте неожиданную смену ключа автоматически; после подтверждённого сброса сохраните старую привязку отдельно. 6. Проверьте S98picklessh локальными тестами из корня репозитория:

      python3 -m unittest discover -s contrib/tests -p test_pickle_ssh.py -v
sh -n contrib/pickle-factory12/S98picklessh

    5. Сверьте штатный init-диспетчер, доступность его команд и порядок перед S99quasar. Передайте скрипт во временный файл в /data, сверьте SHA-256 на обеих сторонах, затем запустите его вручную из root. Существующий неизвестный PID — причина остановиться, не удалить PID-файл. Скрипт сверяет исполняемый файл и полную строку аргументов с NUL-разделителями; имя процесса само по себе не доказывает безопасность.

    6. Откройте второе SSH-соединение на порт 2222 с закреплённым host key, только нужным клиентским ключом и строгой проверкой узла. Подтвердите UID 0. Отдельно отключите public-key authentication на клиенте и получите именно Permission denied (publickey). Тайм-аут и ошибка host key не доказывают запрет входа без ключа.

      На ПК задайте DEVICE, KEY и KNOWN_HOSTS своими локальными значениями. KNOWN_HOSTS должен уже содержать подтверждённый ключ узла для порта 2222. Проверьте вход и отдельный отказ, не включая пароли:

      ssh -p 2222 -i "$KEY" -o IdentitiesOnly=yes \
  -o StrictHostKeyChecking=yes -o UserKnownHostsFile="$KNOWN_HOSTS" \
  -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no \
  "root@$DEVICE" id -u
ssh -p 2222 -o PubkeyAuthentication=no -o BatchMode=yes \
  -o StrictHostKeyChecking=yes -o UserKnownHostsFile="$KNOWN_HOSTS" \
  -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no \
  "root@$DEVICE" id -u

    Флаги проверенного Dropbear — -s -B -j -k -T 3: пароли и перенаправления запрещены, пустой пароль штатного root не мешает входу по ключу. PID-файл находится в /run, все стандартные потоки перенаправлены. Скрипт не останавливает службу: stop ничего не делает, restart отклоняется. Локальный тест использует только синтетические файлы, а не сетевое соединение или настоящий бинарник устройства.

    Закрепите пять изменений в контролируемое окно¶

    Это проверяемый вручную список, не команда для автоматического выполнения. Замена файла не останавливает уже запущенный экземпляр обновления.

    1. Сохраните точные оригиналы четырёх существующих файлов из таблицы на ПК и в /data, их SHA-256, владельцев и права. Для нового S98picklessh подтвердите отсутствие файла; чужой init-скрипт не перезаписывайте. Проверьте исходные суммы, отсутствие неожиданных символьных ссылок, чужих временных файлов и смены загрузки. Для старого ADB используйте побайтовый перенос одного файла с независимой суммой, не двоичный поток через PTY.
    2. Исключите уже выполняющееся OTA. При удерживаемой защите WAN обеспечьте с оператором безопасное неактивное состояние именно updater, сверяя executable и полные аргументы. Не применяйте общий pkill maind, фиксированный PID или непроверенный SIGSTOP. Если безопасного окна нет, остановитесь; Quasar и голосовой launcher не выключайте.

    3. Подготовьте замены из таблицы. Для обеих заглушек проверьте исполняемые права, синтаксис и единственный результат exit 1. Для JSON используйте парсер, не sed: удалите ровно одну задачу updatesd и сравните весь остальной JSON с оригиналом.

      Порядок Путь Ограниченная правка
      1 /system/vendor/quasar/device_ota_update.sh Заглушка отказа до возможного убийства Quasar
      2 /usr/bin/yandex-apply-ota Заглушка отказа
      3 /system/vendor/quasar/launch.json Только задача updatesd
      4 /etc/init.d/S98picklessh Проверенный скрипт, root, 0755
      5 /system/vendor/quasar/activate_adb.sh Только сетевая ветка: adb-net → stop

    4. Откройте корень на запись только на время установки. Замените файлы атомарно по одному в указанном порядке, с проверкой исходных сумм перед каждой заменой. Сохраните USB-ветку ADB и adb_options.inc, штатные rcS, S99quasar, onboot, watchdog, сеть и звук.

    5. Прочитайте установленные файлы независимо: сверьте пять сумм, права и владельцев, неизменность остальных задач Quasar, заглушки OTA и USB-ветку ADB. Не запускайте OTA ради проверки. После доказанного SSH осмотрите штатное состояние ADB и остановите текущий сетевой ADB штатным способом через SSH; подтвердите отсутствие adbd.
    6. Выполните sync и попытайтесь вернуть корень в режим только чтения даже при ошибке предыдущего действия. Проверьте фактические монтирования. На проверенной .8 живой remount в RO не удался: это не PASS. Не повторяйте пакет правок и не форсируйте unmount; защита остаётся до отдельной проверки после обычной перезагрузки.

    На .8 нет iptables/ip6tables. Проверенная политика — управление по SSH, а не обещание фильтра для оставленного сетевого ADB. CA и OTA-verifier сохраняются без изменений.

    Проверьте перезагрузку и уберите временную настройку¶

    1. Согласуйте одну обычную перезагрузку. После неопределённого результата команды сначала прочитайте состояние, не отправляйте её повторно. Подтвердите новую загрузку.
    2. Проверьте без ручного запуска Dropbear: точную .8, UID 0 по строгому закреплённому SSH, реальный отказ без ключа, пять сумм и UBIFS-корень в RO. Подтвердите штатный launcher, platform/media Quasar, отсутствие updatesd и adbd после загрузки.
    3. Восстановите только свои изменения DHCP/DNS. Проверьте действующий resolver самой колонки до остановки сервера: возврат настроек роутера не отзывает старую DHCP-аренду. Если остался DNS компьютера, сохраните оригинал и замените только его на проверенный штатный DNS, сохранив остальные строки, права и владельца. Не запускайте второй DHCP-клиент.
    4. После полной проверки постоянной защиты удалите только свои временные ограничения WAN и точечные исключения, затем остановите проверенные процессы локального сервера. Удалите только свои исключения firewall ПК. Не очищайте весь firewall и не перезагружайте роутер. DHCP-резервацию можно оставить, но с обычным DNS.
    5. Повторно проверьте SSH, версию, RO, отсутствие updater/adbd при обычных DNS/WAN и выключенном сервере настройки. Сохраните копии и результаты приватно, без сырых журналов, ключей и идентификаторов в публичной вики.

    На .8 эти критерии выполнены после одной обычной перезагрузки, включая проверку пяти файлов. Приёмка относится к доступу и OTA-блокировке, а не к голосу или периферии.

    Если не получилось¶

    Симптом Причина или следующий шаг
    После сброса осталась retail Не считать сброс восстановлением factory; остановиться
    Не появилась root-оболочка Проверить отдельно сеть, TLS и ADB; не открывать весь WAN
    Не совпал host key Подтвердить через доверенный root, не отключать проверку SSH
    Скрипт отказал из-за PID Исследовать executable и argv; не затирать чужой PID-файл
    Корень остался RW Приёмка не завершена; не повторять запись и не форсировать отмонтирование
    Исчез DNS после отключения ПК Проверить реальный resolver и вернуть штатный DNS

    Откат и границы¶

    1. Подтвердите рабочий резервный доступ перед откатом. Удаление только init-файла S98picklessh отключает будущий автозапуск, но не останавливает текущий SSH.
    2. Восстановите только нужные оригиналы с проверенными суммами, владельцами и правами в таком же контролируемом окне. Перед возвратом сетевого ADB ограничьте его доступность. Возврат двух OTA-скриптов и launch.json снова разрешает штатные обновления.
    3. Верните корень в RO и проверьте выбранное состояние. Сброс или перепрошивка могут убрать root и ключи; не используйте их как обычный способ отката конфигурации.

    Сообщение сообщества о factory .22 — отдельный результат. Порядок относится только к .8, не к текущей .50.
